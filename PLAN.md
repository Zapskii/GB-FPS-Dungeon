# Speed plan after build E (8.25 fps, 33 images / 4 s)

These are the findings of three planning agents, merged: copy, fill, and
profiling plus C. All costs are hand-counted cycle estimates. Wave 0
measures them for real.

One image costs about 7.3 frames, or about 512k T. Estimated split:

| Stage | Estimate |
|---|---|
| Rays (build E) | about 1.5 frames |
| Fill, colour and mortar passes | 2–2.5 frames |
| `copy_vbuf` (88 T per byte pair, plus mode-3 stalls) | about 2 frames |
| C code | 0.6–1.4 frames |

The copy and the fill are the big targets.

## Rules for the agents

- **One file per agent per wave.** `render.s` is touched by most of these
  changes, so `render.s` work runs one task at a time. Work on other files
  runs alongside it.
- **The main session integrates.** It builds, runs the A/B, bumps the HUD
  build marker, and commits one change per commit.
- **A/B method:**
  - Make a fixed-seed build: `initrand(0x1234u)` in `main.c`, and an fps
    window of 240 frames in `isr.c`.
  - Count images per 4 s in gearboy at the start view.
  - Also measure while holding turn, and while walking.
- **Image check:** a change that should not alter the picture must leave
  `vbuf` identical. Dump it with gearboy `read_memory` (WRAM area 6) and
  compare against the previous build.
- **VRAM timing:** any change to VRAM timing must be re-checked in mGBA or
  on hardware.

## Wave 0: measure (main session)

1. Add the profiling harness, built only with `make PROFILE=1`.
   - `PROF(s)` marks record the frame counter plus the current scanline
     (LY) at each stage boundary.
   - Totals accumulate over 64 images in `prof_acc[7]`, read through
     `read_memory`.
   - Stages: game logic, `render_asm`, `seen[]`, flip wait, copy,
     `sprite_update`, rest.
   - It also counts BFS rebuilds.
2. Record the stage breakdown in the README. Re-rank the waves below if a
   stage turns out very different from its estimate.

## Wave 1: parallel, three agents, one file each

**R1 `render.s`: unrolled ceiling and floor writers**
- Change: replace the 64 T-per-row `bg_copy` with straight-line code
  generated by `tools/gen_bgtab.py`, entered through a computed jump at
  `mxt-1` (ceiling, written with `ld (hl-),a`) and at `mnb` (floor). That
  is about 22 T per row.
- Save: about 27k T, about 0.38 frames, in every view.
- Image must not change. Risk: low.

**C1 `main.c` plus a new `src/math.s`: sprite projection**
- Change: replace the C divide in `project()` (`div16_8`, which goes
  through `__divuint` at about 2.5k T) with a 16/8 shift-subtract in
  assembly (about 500 T), and turn `256/(fwd>>5)` into a lookup table.
- Save: 10–35k T, depending on how many enemies and items are visible.
- Risk: low. A mistake shows up immediately as a misplaced sprite.

**A1 `ai.h`: path-finding rebuild (BFS)**
- Change:
  - Unroll the 4-neighbour loop.
  - Instead of the 1024-byte memset on every rebuild, reset only the cells
    the last search touched. Do one full memset at level load.
- Save: about 50% of each rebuild. One rebuild can currently cost up to
  about 1.5 frames, so this mainly removes stutter rather than raising the
  average.
- Risk: medium. A bug makes enemies freeze, which is easy to spot.

## Wave 2: `render.s` (copy), plus a small edit in `main.c`

**R2: copy only the rows the walls cover**
- Change:
  - `fill_col` records each tile column's span (lowest top, highest
    bottom).
  - A new `_copy_view` copies only the union of this image's span and the
    span last written to the same VRAM bank. The per-bank history
    `ot/of[2][16]` is selected by `r_dst`.
  - Ceiling and floor rows are identical in every column, so the rows it
    skips are already correct.
  - `show_map` must clear the history, because the map overwrites the view
    tiles.
- Save: about 1 frame at the start view (33 → about 38 images per 4 s).
  Less while turning, and nothing when facing a wall up close.
- Optional phase 2: the fill then skips the same rows. Measure it while
  walking, not only on the static view.

## Wave 3: `render.s` (fill internals), one task at a time

**R3: leaner ragged-edge patch**
- Change: walk `r_top`, `r_bot` and `r_clr` with pointers, take the colour
  patterns from a 16-entry table, inline `rg_addr`, and skip rays that
  have nothing to patch.
- Save: about 25k T, about 0.35 frames. Risk: medium (register pressure).

**R4: faster colour pass, with packing merged in**
- Change: run the loop in registers only, reuse the same-face result that
  `od_loop` already works out, and store the colour bits pre-shifted.
- Save: about 22k T, about 0.3 frames.

**R5: move the `seen[]` marking into `render_asm`**
- Change: mark automap cells while the hit pointer is still in a register.
- Save: about 5k T. Trivial. Coordinate with the `main.c` owner, because
  the C loop has to be removed.

## Expected outcome

The estimates do not simply add up, because R2 phase 2 and R1 overlap.
Waves 1–3 together save roughly 2–2.5 frames per image, taking about 7.3
frames down to about 5, or **about 11–12 fps** at the start view.

## Rejected

| Idea | Why |
|---|---|
| Static ceiling/floor tiles | The tilemap is shared by both banks, and only 11 tiles are free. |
| Half vertical resolution with per-line SCY writes | Needs an interrupt on every line, about 36k T per image, with timing risk. |
| Stack-pointer block writes | Needs `di` long enough to risk the VBlank ISR deadline, for about 3k T. |
| Skipping unchanged images | Only helps when standing still. |
